1. AI 코어 프로젝트
1.1 목표
이번 ‘AI 코어 프로젝트’의 목표는 다음과 같다.
-
도메인을 스스로 선택하고(2회차 도메인 이어서 진행 가능), 그 도메인에서 Tool 호출과 판단이 필요한 요청과 외부 API를 정의할 수 있다.
-
사용자 요청을 분석하여 필요한 작업 단계를 스스로 구성하고, 상황에 따라 Tool을 선택하여 호출할 수 있다.
-
외부 API를 Agent가 호출 가능한 Tool로 래핑하고, Tool의 입출력 스키마를 정의할 수 있다.
-
Tool 실행 결과를 통합하여 제약 조건의 충족 여부를 판단하고, 충족하지 못하면 재계획할 수 있다.
-
대화 맥락(Memory)을 유지하여 연속된 요청을 하나의 흐름으로 처리할 수 있다.
-
메인 Agent의 실행 과정을 이벤트로 발행하고, 이를 구독하는 로깅 서브 Agent를 분리하여 구현할 수 있다.
-
생성한 계획과 실행 로그를 저장하고 조회·수정·삭제할 수 있다.
-
FastAPI 기반 백엔드와 프론트엔드를 분리하여 구현하고, Agent 기능을 API로 제공할 수 있다.
-
구현한 기능이 요구사항대로 동작하는지 실행 로그와 실행 결과로 확인하고, 이상이 있으면 어느 단계의 문제인지 진단할 수 있다.
-
심화 과제를 통해 Agent의 역할을 분리하고 실행 결과를 평가하는 멀티 Agent 구조로 확장할 수 있다.

2. 프로젝트 기획
기획 단계에서는 구현에 들어가기 전에 무엇을 만들지 정하고, 그 기획이 실제 외부 API와 도구로 성립하는지 확인한다. 확인을 통과한 설계만 구현으로 넘긴다.
2.1 도메인 확정
-
1일차 16시까지 도메인을 확정하고, 도메인 선택 조건 세 가지를 모두 만족하는지 근거와 함께 적는다.
◼
Tool로 래핑할 외부 API 3종 이상과 각 API가 주는 정보
◼
외부 API의 출처와 이용 조건(호출 한도, 약관)
◼
Tool 결과를 사용자의 제약 조건과 비교해야 답할 수 있는 요청 3개 이상
◼
사용자가 저장 · 조회 · 수정 · 삭제할 결과물
◼
건강·금융처럼 판단이 위험한 도메인인지 여부와, 그렇다면 면책 안내 문구
-
예)KOBIS 오픈API(박스오피스, 영화 상세정보)와 카카오 로컬 API(영화관 검색)를 사용한다. "토요일 3시 이후에 강남에서 영화를 보고 7시 전에 끝내고 싶어"처럼 러닝타임과 시간 제약을 비교해야 답할 수 있는 요청을 기준으로 삼고, 저장할 결과물은 관람 계획(영화, 날짜, 시작 · 종료 시각)으로 정한다.(영화는 판단이 위험한 도메인이 아니므로 면책 안내는 두지 않는다.)
2.2 서비스 시나리오 설계
-
대표 사용자 요청을 정하고, 요청에서 추출할 조건을 기준 조건(날짜, 시각), 선호 조건(지역, 분류), 제약 조건(이후 일정, 상한 금액)으로 나눈다.
-
요청마다 어떤 Tool을 어떤 순서로 불러야 답할 수 있는지 적는다.
-
제약을 충족하지 못해 재계획이 일어나는 요청과, 조건이 모자라 되물어야 하는 요청을 각각 하나 이상 정한다.
-
저장할 결과물의 핵심 값과, 같은 날짜에 시간이 겹치는 결과물이 있을 때의 처리를 정한다.
-
예)요청을 관람 계획 수립, 사실 조회, 관람 계획 확정, 캘린더 등록, 그 밖의 대화 다섯 가지로 나눈다. 관람 희망 시각 없이 "7시 전에 끝나야 해"만 있으면 계산할 시작점이 없으므로 Tool을 부르기 전에 되묻는다.
2.3 Tool 설계
-
Tool마다 이름, 설명, 입력 파라미터, 출력 구조를 정한다.
-
Tool을 외부 API를 감싼 외부 API 툴과 이 서비스 서버가 가진 기능을 감싼 로컬 서버 API 툴로 구분하여 정의한다.
9
.
-
Agent는 설명만 보고 Tool을 고르므로, 설명에는 기능이 아니라 언제 쓰는지를 적는다.
-
모든 Tool이 성공과 실패를 같은 형태로 반환하도록 공통 응답 형식과 실패 코드를 정한다.
-
앞선 Tool의 출력 중 어떤 값이 다음 Tool의 입력이 되는지 정한다.
-
모델의 판단이 필요 없는 작업은 Tool로 두지 않고 실행 흐름이 직접 수행하도록 나눈다.
-
예)필수 Tool은 외부 API 툴 세 개(박스오피스 조회, 영화 상세정보 조회, 영화관 검색)로 나눈다. 심화의 RAG 검색과 일정 조회·등록은 서버가 가진 기능을 감싼 로컬 서버 API 툴이다. 모든 Tool은 ok와 data 또는 error(code, message)로 답하며, 러닝타임이 비어 있으면 NO_RUNTIME으로 구분한다. 관람 계획 저장처럼 사용자가 이미 정한 값을 다루는 작업은 Tool로 두지 않는다.
2.4 Agent 실행 흐름 설계
-
메인 Agent의 실행 단계(의도 분석/계획 수립/Tool 호출/결과 통합·재계획 / 최종 응답)와 단계 사이에 전달할 상태를 정한다.
-
제약 판단에 필요한 값을 어떤 Tool 결과로 계산할지 계산식을 정한다.
-
재계획을 수행하는 조건과 수행하지 않는 조건, 재계획 상한을 정한다.
-
대화 맥락(Memory)에 보관할 것과 보관하지 않을 것을 정한다.
-
예)러닝타임에 더해 관람에 필요한 시간을 구하고, 희망 시각부터 제약 시각까지 비교한다. 충족하는 후보가 하나도 없을 때만 재계획하며 상한은 3회로 둔다. API 키 누락처럼 다시 시도해도 결과가 같은 경우는 재계획하지 않고 바로 안내한다.
2.5 실행 기록과 저장 구조 설계
-
메인 Agent가 발행할 이벤트의 종류와 필드를 정한다.
-
LLM이 내린 판단(의도 분류 등)과 그 이유를 실행 기록에 어떻게 남길지 정한다.
-

2.7 기획 검증
-
2.1 ~ 2.5에서 정한 내용이 실제 외부 API와 도구로 성립하는지 구현 전에 확인한다. 통과하지 못한 항목은 기획으로 돌아가 수정하고, 확인 결과는 기록하여 제출물에 포함한다.
-
도메인 조건 확인 (1일차 16시까지)
◼
외부 API 3종의 키를 발급하고, 각 API를 코드로 한 번씩 호출하여 응답을 받는다.
◼
대표 요청마다 Tool 결과 없이 LLM만으로 답하면 무엇이 틀리는지 한 줄로 적는다. 적지 못하면 요청이나 도메인을 다시 정한다.
◼
16시까지 확인을 통과하지 못하면 제공 도메인 팩(영화)으로 전환한다.
-
Tool 설계 확인
◼
실제 응답을 Tool의 출력 구조에 맞춰 보고, 제약 판단에 필요한 속성이 응답에 들어 있는지 확인한다.
◼
값이 비어 오거나 결과가 없는 경우의 실제 응답을 확인하여 실패 코드에 반영한다.
◼
각 출처의 호출 한도와 이용 조건을 확인한다.
-
도구 연결 확인
◼
LLM API를 한 번 호출하여 응답을 받는다. (API 키, 접속 주소, 환경변수 로딩)
◼
Tool 명세를 함께 넘겼을 때 LLM이 Tool 호출을 선택하는지 확인한다.
-
설계 시험
◼
대표 요청 하나를 설계한 실행 단계와 Tool 호출 순서대로 따라가며, 각 Tool의 입력이 요청 분석 결과나 앞선 Tool의 결과로 모두 채워지는지 확인한다.
◼
재계획이 일어나는 요청으로 재계획 조건과 상한이 설계대로 동작할 수 있는지 확인한다.

메인 Agent 구조 분리
②
요구사항 번호: F3021
◆
메인 Agent를 계획 수립(Planner)과 작업 수행(Worker) 역할로 분리해야 한다. Worker는 필수 구현의 외부 API 툴을 그대로 호출한다.
◆
Planner는 사용자 요청을 작업 목록으로 분해하고, Worker는 각 작업을 Tool 호출로 수행해야 한다.
◆
Planner와 Worker는 작업 목록과 수행 결과를 정해진 형식으로 주고받아야 한다.
◆
Planner, Worker, 로깅 Agent는 모두 LLM을 사용할 수 있어야 하며, Agent마다 LLM을 호출하는 조건을 정의해야 한다. 규칙으로 판단할 수 있는 상황에서는 LLM을 호출하지 않는다.
◆
Worker는 Tool이 인자를 고치면 결과가 달라질 수 있는 실패(결과 없음, 대상 없음, 잘못된 입력)를 반환했을 때만 LLM으로 재시도, 건너뜀, 계획 변경 요청 중 하나를 판단해야 한다. 재시도는 같은 Tool로만 상한 횟수 안에서 수행하며, Planner가 사용자 조건으로 고정한 인자는 바꾸지 않아야 한다.
◆
Worker가 스스로 해결하지 못한 실패는 사유와 함께 Planner에게 전달하고, Planner는 이를 재계획에 반영해야 한다.
◆
수행 결과의 검증은 로깅 Agent가 담당하며, 이상으로 판단되면 Planner가 작업 목록을 다시 구성해야 한다.
22
.
◆
구조 변경 전후의 실행 흐름과 재계획 횟수를 비교하여 정리해야 한다. Worker의 LLM 판단을 켠 경우와 끈 경우의 재계획 횟수, 요청당 LLM 호출 수, 응답 시간도 함께 비교한다.
◆
예)Planner는 작업 목록을 만들면서 사용자 조건으로 채운 인자(지역, 날짜, 영화코드)를 고정 인자로 표시한다. Worker는 평소에는 LLM 없이 작업 목록대로 Tool을 부르고, 지목한 영화관 이름으로 검색했다가 결과 없음(NO_RESULT)이 나온 경우처럼 인자를 고칠 여지가 있을 때만 LLM에게 묻는다. API 키 오류 같은 치명적 실패, 필수 인자 누락, 같은 이름의 지역이 여러 곳인 경우(AMBIGUOUS)는 사용자에게 되묻거나 멈출 일이므로 LLM에게 넘기지 않는다. 작업 목록과 Worker의 판단을 이벤트로 남기면 로깅 Agent가 계획에 없던 호출과 고쳐 부른 호출을 구분할 수 있다.

4. 검증
3장의 요구사항이 실제로 충족되었는지 확인한다. 확인은 실행 결과로 증명하며, 증명이 필요한 항목은 해당 화면이나 실행 로그를 캡처하여 첨부한다.
4.1 Tool 확인 (F3001 ~ F3004)
-
등록한 Tool의 이름 · 설명 · 입력 스키마 목록을 출력하여 명세와 일치하는지 확인한다.
-
Tool마다 정상 호출과 실패 호출(잘못된 입력, API 키 없음 등)을 각각 실행하여, 예외가 밖으로 나오지 않고 실패 응답 형식으로 반환되는지 확인한다.
-
후보 목록 Tool에 기준 날짜를 주지 않았을 때 정의한 기본값이 적용되는지 확인한다.
-
요청한 기준과 실제로 조회한 기준이 다른 경우(예: 미래 날짜) 그 사실이 응답에 밝혀지는지 확인한다.
-
후보 목록 Tool이 반환한 식별자를 상세정보 Tool에 넘겨 조회가 이어지는지 확인한다.
-
판단에 필요한 속성이 비어 있는 항목이 임의의 값으로 채워지지 않고 판단하지 않은 채 남는지 확인한다.
-
보조 정보 검색 Tool에서 결과가 없는 경우의 응답 형식이 정의대로 나오는지 확인한다.
4.2 메인 Agent 실행 흐름 확인 (F3005 ~ F3011)
-
하나의 요청에서 추출된 조건(기준, 선호, 제약)을 출력하고, 요청에 없던 조건이 임의로 채워지지 않았는지 확인한다.
-
LangGraph 그래프가 분석 → 계획 → 실행 → 판단 → 응답 노드로 구성되어 있는지 확인한다. (그래프 구조 출력 또는 코드 캡처)
-
같은 요청에서 Tool이 필요한 경우와 필요 없는 경우(인사, 사용법 질문)의 계획이 서로 다른지 확인한다.
-
앞선 Tool의 결과가 다음 Tool의 입력으로 전달되는지, Tool 하나를 일부러 실패시켜도 나머지 단계가 진행되는지 확인한다.
24
.
-
제약 판단에 쓴 계산 값(필요 시간 등)과 충족 여부가 응답의 판단 기준과 일치하는지 확인한다.
-
외부 API로 확인할 수 없는 값을 지어내지 않고 역산한 기준으로 제시하는지 확인한다.
-
충족하는 후보가 없는 요청으로 재계획을 일으켜, 이미 확보한 Tool 결과가 다시 호출되지 않는지 확인한다.
-
재계획이 상한에 도달하도록 만들어, 멈추고 사유와 함께 응답하는지 확인한다.
-
"같은 조건에서 하나만 바꿔서" 같은 후속 요청에서 바뀐 조건만 갱신되고 나머지 조건이 유지되는지 확인한다.
-
응답에 추천 항목, 보조 정보, 판단 기준, 근거 Tool 결과가 함께 표시되는지, 제외한 후보에 제외 사유가 있는지 확인한다.
-
건강 · 금융처럼 판단이 위험한 도메인이면 답변에 전문가 조언을 대신하지 않는다는 안내가 표시되는지 확인한다. (해당 도메인만)
4.3 로깅 Agent와 실행 로그 확인 (F3012 ~ F3014)
-
요청 1건을 실행한 뒤, 단계 진입 · 종료와 Tool 호출 요청 · 응답 · 소요 시간이 이벤트로 발행되었는지 확인한다.
-
LLM이 내린 판단(의도 분류 등)과 그 이유가 이벤트에 남는지 확인한다.
-
로깅 Agent가 이벤트를 수집하고 저장하는 과정에서 LLM을 호출하지 않는지 확인한다.
-
로깅 Agent를 연결하지 않고 실행해도 메인 Agent가 정상 동작하는지 확인한다. (발행이 구독자에 의존하지 않는지 확인)
-
로깅 Agent가 이벤트를 세션 단위로 구분하여 저장했는지, 서로 다른 세션의 로그가 섞이지 않는지 확인한다.
-
실행 로그 목록 조회, 특정 세션의 상세 조회(실행 순서대로), 삭제가 각각 동작하는지 확인한다.
-
실행 로그를 수정하는 API가 존재하지 않는지 확인한다.
4.4 계획 관리 확인 (F3015 ~ F3016)
-
최종 계획을 저장하여 핵심 값과 생성 일시가 목록과 상세 조회에 나타나는지 확인한다.
-
같은 날짜에 시간이 겹치는 계획을 저장했을 때 저장은 되고, 겹치는 계획이 저장 결과와 함께 알려지는지 확인한다.
-
계획의 핵심 값 수정과 삭제가 되고, 그 결과가 화면 목록에 바로 반영되는지 확인한다.
4.5 서비스 구성과 화면 확인 (F3017 ~ F3019)
-
대화 요청, 계획 관리, 실행 로그 조회 API가 서로 다른 경로로 동작하고 요청 · 응답이 정의한 형식과 일치하는지 확인한다. (FastAPI 문서 화면 캡처)
-
대화 화면과 계획 관리 화면이 모두 백엔드 API를 호출하여 데이터를 표시하는지 확인한다.
-
답변과 함께 실행 단계와 Tool 호출 이력이 실행 순서대로 표시되고, 재계획 지점이 구분되는지 확인한다.
25
.
-
처리 중 상태가 표시되는지, Tool 실패와 API 키 누락 상태로 실행했을 때 안내가 표시되는지 확인한다.
4.6 심화 기능 확인 (F3020 ~ F3023)
-
선택한 심화 과제만 확인한다.
-
F3020
◼
같은 Tool을 같은 입력으로 반복 호출한 실행, 재계획을 과도하게 반복한 실행, 계획에 없던 Tool을 호출한 실행을 각각 만들어 이상 징후로 식별되는지 확인한다.
◼
근거가 되는 이벤트가 없을 때 '이상 없음'이 아니라 '판정 불가'로 남는지 확인한다.
◼
판단 결과를 메인 Agent가 참조할 수 있는지 확인한다.
◼
이상으로 판정한 실행에만 원인 진단이 붙고, 정상 실행에는 LLM이 호출되지 않는지 확인한다.
-
F3021
◼
Planner의 작업 목록과 Worker의 수행 결과가 정해진 형식으로 오가는지 확인한다.
◼
로깅 Agent가 이상으로 판단했을 때 Planner가 작업 목록을 다시 구성하는지 확인한다.
◼
Planner, Worker, 로깅 Agent 사이의 메시지가 실행 로그에 남는지 확인한다.
◼
구조 변경 전후의 실행 흐름과 재계획 횟수를 비교한 결과가 있는지 확인한다.
◼
정상 경로에서 Worker의 LLM 호출이 0회이고, 치명적 실패와 필수 인자 누락에서는 LLM이 호출되지 않는지 실행 로그로 확인한다.
◼
Tool이 결과 없음으로 실패했을 때 Worker가 LLM 판단으로 인자를 고쳐 같은 Tool을 다시 부르고, 고정 인자는 바뀌지 않는지 확인한다.
◼
Worker가 올린 계획 변경 요청이 Planner의 재계획에 반영되는지 확인한다.
-
F3022
◼
외부 API로 확인할 수 없는 질문에 RAG 검색 Tool이 선택되어 호출되는지 확인한다.
◼
응답에 근거 문서와 출처가 함께 나오는지 확인한다.
◼
색인이 없는 상태에서 정의한 응답 형식(NO_INDEX 등)이 나오는지 확인한다.
-
F3023
◼
일정 조회와 등록이 로컬 저장소 구현체로 먼저 동작하는지 확인한다.
◼
구현체를 Google Calendar 연동으로 바꿔도 Tool의 입출력 형식이 그대로인지 확인한다.
◼
조회한 일정이 제약 적합성 판단에 반영되는지 확인한다.

-
화면에 API 키와 오류 상세 내용이 노출되지 않는지 확인한다. (NF3002)
-
Tool 호출이 실패해도 서비스 전체가 중단되지 않는지 확인한다. (NF3003)
-

-
대표 요청의 전체 처리 시간이 사용에 지장이 없는지 확인한다. (NF3005)
-
프론트엔드와 백엔드가 분리되어 있고, Agent와 Tool 코드가 파일로 나뉘어 있는지 확인한다. (NF3006)
-
사용한 외부 API의 출처와 이용 조건(호출 한도, 약관)을 기록했는지 확인한다. (NF3007)
